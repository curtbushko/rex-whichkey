# Experimental validation update — 2026-10-30

## Executed experiments and results

Reproducible source: `docs/experiments/rex-validation/README.md` and `run.sh`. Selected actual transcripts are in that directory's `results/`. These are test artifacts, not another task/status database. The independent nested Go module pins dependencies without changing application go.mod/go.sum or the root Taskfile/linter configuration.

### Persistent Rex Lua runtime and launch/selection lifecycle — PASS within tested scope

Started a separate Unix-socket Rex server with its own Lua config and state directory. Version 0.0.1793359647-g966596, API revision 8. It did not replace or restart the user's older connected server. A sibling user configuration module loaded in the real server's init.lua environment, not merely `rex config check` or a script-local action.

The launcher records the origin and a test invocation ID in a Lua table, creates a terminal layer, and returns. Initially a shell probe and subsequently both compiled Go probes send data-only selection arguments back through the Rex CLI. A registered configuration action looks up a Lua closure and executes it in the persistent server Lua runtime. Callback arguments, context and a persistent invocation/callback counter survived independent CLI calls. No Lua function was serialized.

Passed explicit tests for: two overlapping invocations finishing in reverse order; duplicate live-ID rejection; consumed-selection replay rejection; required confirmation; unknown-selection rejection; cancellation without callback; immediate-expiry rejection; wrong-origin-block rejection; moving the origin block into another window and focusing it before callback; config reload invalidating old invocation state; and successful fresh invocation after reload.

Both compiled Go probes completed popup → CLI → registered server-side Lua callback with exact originating session/block IDs. A Go popup remained running 31 seconds after the launch action returned and then dispatched successfully. Thus a short launch action plus terminal-owned process lifetime is viable without holding the action open for user interaction or introducing a daemon.

Scope limits: the origin client in these experiments is a real CLI connection, not a graphical app. Preserving its captured ID demonstrates data/context plumbing, not successful app action queueing after a popup. The dispatcher uses fixture IDs and compares session/block identity, not a production authentication/token scheme. Cryptographic tokens, bounds/expiry limits, client ownership, missing-origin errors, stale conditions, callback crashes, app-client routing and reentrant dispatch still need production design/tests. This prototype must not be adopted unchanged.

### Native layer API geometry — PASS; visual geometry — BLOCKED

For top/bottom/left/right/center, created native layers with the intended fractional bounds, verified the returned bounds in session.view, captured a complete numbered 40x12 grid including edge markers, changed layer bounds, verified the new bounds, observed terminal exit, explicitly closed only the returned layer IDs and verified removal.

The isolated server had no GUI client. Its terminal size came from explicit creator options, not actual app-owned layout sizing. This validates server schema/placement/resize/cleanup contracts, not clipping, opacity or client-driven terminal resize. `screencapture -x -o ...` on the research machine failed with `could not create image from display`. No app focus or display permissions were changed. Current visual clipping remains unverified; do not infer it is fixed from captures or from the floating-pane release.

A useful lifecycle finding: `rex wait` can fail target resolution if a very short-lived block has already disappeared. Grid probes retain their exited block until wait can read its exit result, then explicitly close the exact owned layer. Do not blindly retry creation because a wait target vanished.

### Compiled TUI comparison — MEASURED, neither candidate accepted unchanged

Environment: Go 1.25.5 darwin/arm64; GOTOOLCHAIN=local, GOMAXPROCS=4. Tested Bubble Tea v2.0.0 initially, then v2.0.8 for the retained experiment. Latest v2.1.1 and v2.0.10 require Go 1.26; no toolchain or application dependencies were upgraded to accommodate them. Retained candidate dependency versions are pinned in the experiment module.

Final clean reproduction, 20 samples/candidate:

| Measurement | Minimal direct I/O | Bubble Tea v2.0.8 |
| --- | ---: | ---: |
| First terminal content, observed median | 15.071 ms | 33.993 ms |
| First content, p95 | 18.331 ms | 34.772 ms |
| Selection key to restored process exit, observed median | 17.358 ms | 17.743 ms |
| Selection key to restored process exit, p95 | 21.417 ms | 18.495 ms |
| Unstripped compiled binary size | 3,082,706 bytes | 5,321,714 bytes |

Method: start a fresh PTY and shell wrapper; capture stty state, launch a compiled binary, wait for the first content marker, send y, verify mode restoration and process exit. Timings include PTY/shell/stty overhead, exclude compilation, and for these samples exclude callback RPC. These are warm local observations, not cold-cache Go-only times, real-app pixel first-paint times, or remote latency. No product latency threshold was invented. The direct parser is intentionally less capable, so speed alone is not an equivalent-feature comparison.

Selection, q/Escape dismissal, Tab/Backspace input, 40x12 resize, ASCII output, uncolored NO_COLOR compatibility, intentional error return and terminal-mode restoration passed in the PTY harness. This does not establish all mapping/navigation/theme requirements. Probe views contain no SGR colors, so NO_COLOR is not a full theme test.

Terminal restoration initially failed an overstrict byte-for-byte comparison: Darwin changed lflag PENDIN (0x20000000), a kernel-maintained pending-input flag, while all configured modes/control characters matched. The retained comparison excludes only that transient bit on Darwin, retaining all other fields. An application-owned terminal-state snapshot surrounds both candidate lifecycles. This observation is not evidence of a Bubble Tea restoration bug; an initial NOKERNINFO hypothesis was disproved by checking the platform constants (NOKERNINFO is 0x02000000).

### Discovered candidate limitations — UNMET product gates retained explicitly

1. Injecting an OSC background-color response (`ESC ] 11;rgb:2222/3333/4444 BEL`) followed by y makes the minimal direct parser cancel on the response's Escape byte. Bubble Tea correctly treats that response as a terminal message rather than the Escape key. Direct I/O needs a real escape/terminal-reply parser before adoption.
2. The tested Bubble Tea renderer drops U+0301 in decomposed `e` + combining acute, while retaining the CJK character and base e. The direct probe preserves the bytes. This was observed in raw PTY output and reproduced through a real terminal block on the isolated Rex server. Root cause is not established; it may involve renderer/width negotiation. Precomposed normalization alone is not an accepted general Unicode fix.

The normal research suite records these observations and can pass without satisfying product acceptance. A separate strict Unicode check (`WK_STRICT_UNICODE=1 go test -count=1 -v -run TestUnicodeObservation ./internal/probe`) intentionally still fails for Bubble Tea. Its actual failure is retained in `results/unicode-acceptance.log`; the reproducible runner prints UNMET. No framework is selected, no regression is waived, and there is no claim of full Unicode/theme acceptance. A renderer correction, another compatible version/framework, or another proven approach must clear this criterion before adoption.

## Design implications and remaining decisions

- The Lua-runtime callback/configuration model is technically viable. Prefer a short launcher and terminal-owned lifetime. Define a data-only selection contract with explicit origin and reload/stale-selection behavior. Do not transplant fixture-ID security or assume app-client routing is covered.
- Effective known-host discovery and static delegation to Rex's session picker remain supported by the earlier research. Menu-host versus originating-client/home inventory ownership still needs an explicit user-facing contract.
- No native-layer workaround is selected without actual graphical verification. Keep that visual test as a specific geometry adoption gate rather than blocking unrelated client/mapping research.
- TUI startup differences are measured; full terminal correctness remains decisive. The combining-mark failure blocks accepting the tested Bubble Tea path unchanged, while the terminal-response failure blocks accepting the minimal direct path unchanged.
- Research does not require pre-approving unknown research outcomes. A phase graph can contain a bounded research/design milestone with dependent implementation gated on its resulting contracts. No phase/task manifest or final interface design is approved by this experiment report.

## Findings by source section 10

### 10a — Lua callback and Go dispatch boundary

Confirmed: `rex.action` registers a named Lua callback; action names use lowercase letters, digits and underscores, not dots. `rex do SCRIPT --action NAME` can load and invoke a script-local action without reloading config. A harmless real CLI probe invoked a closure with a string argument and returned the originating session/block/client IDs. No Lua function was serialized to Go.

The old plugin registers launch, snapshot and dispatch actions. It retains callbacks and action arguments in Rex, looks up mappings at dispatch, focuses the originating block, then calls a callback or queues the client action. This is useful behavioral evidence, not a required transport or snapshot architecture.

Important published constraints: configuration actions have a 30-second lifetime; commands started by an action normally die when it returns unless detached. A menu must therefore not hold a launch action open awaiting user input. Prefer a terminal block lifecycle for the menu, with a short launch action that returns. `rex.client.queue` defers app actions until a configuration callback returns and discards them if it fails; script-mode queue calls execute immediately. `client.action` is not a generic route for app actions such as pane.split: use CLI `rex -C CLIENT do ACTION`/the supported client routing. `client.perform` timeouts do not guarantee that the app will never execute the action, so do not automatically retry destructive dispatch.

Proposed contract IF-LAUNCH: capture explicit origin server/session/block/client and resolved window before launching. Pass only data through an argument array; never use an eval string made from config. Popup block identity must remain separate from origin identity. Resolve block location at dispatch rather than relying permanently on its original window.

Proposed contract IF-DISPATCH: Go returns an opaque mapping/selection identity plus confirmation state to a Rex-side dispatcher. Lua retains executable callbacks. Dispatcher validates the invocation, selection, current origin and confirmation before executing. Expiry, replay protection, config-reload behavior, overlapping menus, stale conditions and the exact data channel are unresolved; do not copy the old protocol as the default. Remote ownership of the Lua runtime must be explicit.

Remaining experiment: an isolated, temporary-config Rex server must demonstrate launch → selection → persistent Rex-runtime callback with exact origin IDs; two concurrent invocations, reload during a menu, dismissal, stale selection, timeout and duplicate dispatch must be exercised. The script-local probe alone does not validate this full round trip.

### 10b — Inline and separate Lua configuration

Confirmed in published docs: init.lua can require sibling Lua modules, and config lives on the server host. `rex config reload` is refused over a remote connection. The CLI Lua runtime reports Lua 5.1, require and dofile functions.

Executed `rex config check /tmp/.../probe/init.lua --json`: no diagnostics and one correctly typed action. The probe required a sibling `whichkey_user_config.lua` without modifying package.path. Executed the same file using `rex -C m4-pro do ... --action whichkey_research_probe marker=callback-ok --json`: returned marker=callback-ok, position=left and description=external, plus the expected nonempty origin IDs. The merge in the probe was explicitly authored by the probe, not a Rex-provided precedence rule. Observed ctx.origin was api despite the CLI help's cli default: treat origin as diagnostic, not an authorization signal.

Proposed public contract IF-CONFIG: install an integration module named rex_whichkey and let a distinctly named user module return a configuration table. Both `setup({spec=...})` and `setup(require('whichkey_user_config'))` use the same API. One table is supplied per setup call; no implicit merge of inline/file specs. Defaults apply only where values are absent. Reject duplicate setup unless replacement semantics are deliberately specified. This API is a proposal, not an existing promise.

Remaining: test real server init.lua loading and packaging-generated module search paths in an isolated config; ensure failures do not damage the last working setup. Nix paths must exist on the target server, not merely the initiating client.

### 10c — Native layer clipping

The live server advertises session.new_layer and session.resize_layer. Bounds accept [x,y,w,h] fractions or the legacy object form; width/height are dimensions and the rectangle must fit in the window. Layer creation defaults focus=false; request focus explicitly when required.

Historical evidence remains cautionary: feedback 1560653603151282378 is active; it reports a correct captured grid but clipped rendering at offset bounds. Feedback 1559241103117656144 is deferred and describes the same width-versus-right-edge issue. The Oct 27 floating-pane release announcement does not establish that this exact issue is fixed in the installed build.

Not validated: current visual clipping, opaque background behavior, all five positions or resize. API success, text capture and terminal-reported size cannot prove visual correctness.

Next experiment: in an isolated research session, render numbered edge/corner markers in native top/bottom/left/right/center layers, resize each and compare reported size, capture and actual app screenshot. Repeat with content behind the layer and nonzero offsets including x>w. Record app/server versions. Compare full-window overlay only if native geometry fails; no workaround has been selected. Closing probes must use only returned IDs and restore focus.

### 10d — Rex-known host discovery

Confirmed directly: `rex hosts --json` returns an effective inventory with home status, nested hosts[].host records, per-entry from/held and warnings. On this machine it lists one known host. It does not require a Tailscale inventory.

Installed help: effective inventory combines home hosts with this machine's hosts; local duplicate labels win, and unreachable-home information may be cached. --server/REX_SERVER do not retarget `rex hosts`. Distinguish this CLI result from raw `hosts.list`, which lists one server's hosts and hash/diagnostics rather than the merged CLI wrapper.

Read-only connectivity check `rex -S gamingrig --timeout 5s whoami --json` succeeded over Tailscale and reported an older remote server with zero sessions. This validates label routing/identity only, not remote popup launch or session reuse/create.

Proposed IF-HOSTS: use the CLI's effective inventory for the initial menu, preserve stable host IDs and labels, display warnings/cached-home state, and do not add/update hosts or proactively probe every endpoint. If the menu runs on a remote server, document whose effective inventory is intended: originating client/home versus menu process host. That user-visible choice remains open.

### 10e — Dynamic/session parity

Old config.lua contains static mappings for session.new/switch/previous/next/rename/close. Its dispatch queues the chosen app action. It does not generate a session-name submenu. Old tab-number entries 1–9 are statically generated at configuration time.

The connected app advertises session.switch titled "Change Session…", plus session.select(session_id, optional window_id). Its action catalog includes all old default action names; pane.split uses up/down directions whereas CLI split uses above/below. Do not reuse argument vocabularies between those interfaces.

Conclusion: preserve the delegated Rex session picker as the functional baseline; a dynamically enumerated popup submenu would be additional scope, not required parity established by the old code. Interactive picker behavior was not exercised to avoid disrupting the user's app.

### 10f — Flat concrete Go Rex package

Live schemas support the Client/Session/Window/Block resource model. Keep a single rex package with concrete values and a low-level Call escape hatch; no service hierarchy or interface-per-resource. A resource must carry stable server/session targeting independent of window membership. Resolve moved-block locations with supported inspection rather than deriving session identity from a cached window.

Separate CLI effective host inventory from raw Server API calls. Distinguish client app actions from server resource operations. Construct CLI args as arrays and decode typed JSON; use a small process-runner seam if needed for unit tests, not an exported transport hierarchy.

No Go signatures or architecture were implemented. This research supports the already accepted concrete-type direction; exact exported methods remain design work.

### 10g — TUI framework versus direct I/O

Documentation review only: Bubble Tea's current upstream README describes v2 (`charm.land/bubbletea/v2`), an Elm-style model/update/view event loop and managed terminal rendering. Tcell describes a cell-oriented terminal abstraction, grapheme/color support and automatic capability negotiation. Direct I/O would leave raw mode, escape parsing, resize, redraw, terminal queries and restoration to this project.

Recommendation for the comparison spike: start with Bubble Tea versus minimal direct I/O, keeping pure mapping/navigation state independent of the renderer; consider tcell if explicit cell geometry or capability behavior warrants it. Do not infer that a terminal framework requires a layered/hexagonal application architecture.

Not measured: startup/first-paint latency, allocation/binary-size cost, OSC palette query interaction, PTY cleanup, key/resize latency or remote behavior. No dependency/version is selected. Pin candidate versions before comparing, run compiled binaries repeatedly in the same Rex popup/PTY, and record distributions rather than go-run compilation times. Check Unicode width/graphemes, NO_COLOR/ASCII, Esc/Backspace/Tab, cancellation/error restoration and very small dimensions. No numerical performance acceptance threshold exists in the requirements; seek a product threshold rather than inventing one.

## Security, rollout and rollback

No persistent user configuration changes were made. Probes were loaded as script-local actions and ended immediately. Keep arbitrary user callback code only in its trusted Lua runtime. Do not infer authorization from ctx.origin, accept client-local paths for remote execution, interpolate config into a shell, or retry timed-out destructive requests automatically.

A future spike should use an isolated Rex server/config or explicit temporary research session. Retain source and returned resource IDs; remove only owned resources after confirming completion. Do not reload/replace the user's init.lua or restart any existing Rex server. Production adoption waits for version-specific integration evidence and user-approved contracts; rollback means disabling the new launcher without taking ownership of the rest of init.lua.

## Reproducible harmless configuration/callback probe

Sibling file whichkey_user_config.lua:

```lua
return { position = 'left', spec = { { 'x', desc = 'external' } } }
```

Probe init.lua (not the user's configuration):

```lua
local external = require('whichkey_user_config')
assert(external.position == 'left', 'sibling module failed')
local config = { position = 'center', spec = { { 'x', desc = 'inline' } } }
for key, value in pairs(external) do config[key] = value end
rex.action{
  name = 'whichkey_research_probe',
  title = 'WhichKey research probe',
  args = { marker = 'string' },
  run = function(ctx, args)
    local callback = function(origin, input)
      return { marker = input.marker, position = config.position,
        description = config.spec[1].desc, session_id = origin.session_id,
        block_id = origin.block_id, client_id = origin.client_id,
        server = origin.server, origin = origin.origin }
    end
    return callback(ctx, args)
  end,
}
```

Run `rex config check PATH/init.lua --json`, then `rex -C CLIENT do PATH/init.lua --action whichkey_research_probe marker=callback-ok --json`. These commands do not install the action into the running configuration. Observed: config check diagnostics=[], marker=callback-ok, position=left, description=external and populated origin session/block/client IDs; origin=api. Temporary source clones/docs/raw API output live under /tmp/rex-whichkey-research and are not authoritative workflow records.
