# Phase 15: Code-owned runtime discovery and compatibility

## Context and authorization

The user rejected hardcoded runtime wiring in init.lua and in Nix, then explicitly requested a new phase. Capture the agreed ownership correction REXWHICHKEY-20261104-193124 in this existing project; do not begin implementation as part of phase creation.

Source evidence shows a split between the locally rebuilt public executable and the helper/Lua dispatcher used by the registered action. Runtime path injection and manual binary/Lua pairing have produced repeated stale-component failures, flashing popups and rename selections rejected before their resource API call. This phase fixes responsibility and coherent startup, not only one installation's literal path.

Authoritative scope: designs/rex-whichkey-runtime-ownership.md. Preserve REQ-002, REQ-003, REQ-005, REQ-011, REQ-013, REQ-014, REQ-016 and REQ-017; the design explains this phase's complementary contribution rather than claiming to redeliver all earlier work.

## Scope

Move execution-host CLI/helper discovery, self-spawn selection and runtime compatibility into application code. Keep normal packaging as build/install and user init.lua as keybindings/customization. Reconcile public CLI, registered key/palette launch, configured completion and development/package entrypoints without losing the original-server Lua callback registry.

Preserve the existing WhichKey tab/session rename pages and authenticated resource updates while removing the need for users to coordinate helper and Lua versions manually. This is not a request to bypass Lua customization, rename through Rex UI, or hardcode the same filesystem paths in another language.

## Acceptance criteria

1. Ordinary CLI and keybinding launch require no helper/rex_bin_dir constructor entries, Nix-store/repository binary literals, generated path substitution, or socket literals in init.lua. Existing explicit server/client intent options remain valid.
2. Application code resolves and validates the Rex CLI and related runtime components on the execution/server host using documented, trustworthy sources. Supported app-launched restricted-PATH operation must not depend on manually repairing server PATH. Unsupported/ambiguous contexts fail safely before mutation; do not guess user-specific directories or probe alternate endpoints.
3. The public caller, helper/controller and PTY child use a coherent executable/asset/protocol selection. A normal local rebuild does not accidentally defer to a stale installed helper merely because a Lua action is registered. A packaged install has the same behavior without Nix owning runtime logic.
4. Users do not maintain binary/Lua version pairs to make ordinary launch or rename work. Code handles supported compatibility and detects unsupported combinations before a flashing popup, dropped selection or wrong action. Do not silently switch away from configured custom mappings after failure or uncertainty.
5. Nix/Home Manager only build/install binaries and normal assets; runtime decisions, constructor path injection and application dependency resolution are removed from their responsibility. No external consumer configuration, user init.lua or live Nix profile is edited/activated automatically.
6. Preserve original-VM callbacks, separately retained GUI target/caller identity, exact endpoint/session/block/resource IDs, connection/configuration/expiry checks, capability privacy, confirmation, consume-before-dispatch, owned-only cleanup and no uncertain retries. Do not add a daemon, direct socket client, replacement Lua VM or automatic reload/restart.
7. Default tab and session rename open the existing WhichKey page and retain safe text/resource binding through successful completion; custom callbacks remain their original actions. Missing/incompatible text support must not fall through to a Rex dialog or silently claim success.
8. Public help, examples and migration notes describe one code-owned startup model for development and installation. Remove instructions that present hardcoded helper paths, manual component pairing or repeated flake refreshes as runtime fixes. Distinguish source-reviewed intent, compiled results and actual observed behavior.

## Expected implementation areas

- cmd/main.go, launch.go: public entrypoint and route/bootstrap selection.
- rex/exec.go and rex/endpoint.go: centralized documented CLI resolution, execution-host provenance and endpoint policy.
- popup.go and native_text_entry.go: exact self-spawn identity, configured presentation/completion and safe controller diagnostics.
- lua/rex_whichkey.lua and lua/rex_whichkey/dispatch.lua: minimal original-VM integration, stable compatibility and removal of required execution path wiring.
- mapping.go and docs/mapping-format.md only if a shared contract actually needs refinement; Go remains format owner and Lua a consumer.
- nix/package.nix, nix/home-manager.nix, flake.nix and README/docs: build/install boundaries, not a new runtime resolver in packaging.

These are expected interface areas, not concurrent ownership reservations. The Task Manager must first inspect the current uncommitted work and assign bounded, reviewable tasks. Do not overwrite, auto-stash, migrate or attribute the existing repairs as this phase's completed implementation. Preserve project-level Taskfile/lint/hook standards.
